# Архитектура Compact Guard

Для тех, кому интересно, как это работает внутри, и для тех, кто собирается править код. Пользовательская часть — в [README.md](../README.md).

Факты о поведении Claude Code, на которые опирается конструкция, проверены живыми тестами и записаны в [SPIKE.md](SPIKE.md); ссылки на пункты SPIKE стоят там, где решение неочевидно. Требования — в [specs/compact-guard-tz-v1.md](specs/compact-guard-tz-v1.md), решения по расхождениям с ТЗ — в [plans/compact-guard-plan.md](plans/compact-guard-plan.md).

## Три роли и одна идея

Идея всей конструкции в одной фразе: **факты живут вне записки**. Агент сжимает контекст и пишет себе резюме, но параллельно с этим плагин ведёт собственный журнал ошибок на диске. Потерять или переписать журнал записка не может, потому что он не проходит через модель. Сверка «журнал против того, что агент сказал» и есть защита.

- **Инструктор** влияет на текст записки заранее: правила в `additionalContext` на каждом `SessionStart` и, если пользователь запустил `init`, блок в CLAUDE.md проекта.
- **Инспектор** читает записку сразу после сжатия и сверяет её с журналом.
- **Ревизор** на `Stop` сверяет финальный ответ агента с журналом и при нехватке блокирует завершение хода.

## События и обработчики

Все хуки — один вход: `node "${CLAUDE_PLUGIN_ROOT}/scripts/cg-hook.js" <Event>`. Скрипт читает stdin, диспатчит по событию.

| Событие (matcher) | Что делает |
|---|---|
| `SessionStart` (`startup`, `resume`, `clear`, `fork`) | Инструктор: правила в `additionalContext`. На `startup` ещё и ротация старых файлов |
| `SessionStart` (`compact`) | Инструктор повторно; Инспектор-1 (резюме из транскрипта, архив, классы находок, карточка); **всегда** — список открытых ошибок журнала в `additionalContext` |
| `PostCompact` (`manual`, `auto`) | Отметка компакции в журнале; архив сырого `compact_summary`; в режиме `strict` — Инспектор-2 |
| `PostToolUseFailure` (все инструменты) | Регистратор: новая запись об ошибке либо `count++` у открытой записи с той же сигнатурой |
| `PostToolUse` (`Bash`, `PowerShell`) | Закрытие записи, если та же команда прошла успешно; эвристики упавших тестов в stdout |
| `UserPromptSubmit`, `PreToolUse` | Доставка отложенных сообщений из очереди, если она непуста; иначе мгновенный выход |
| `Stop` | Ревизор |

Порядок при `/compact` — `PreCompact → SessionStart(compact) → PostCompact` (живой тест 3). Это контринтуитивно: `SessionStart:compact` идёт **до** `PostCompact`. Поэтому Инспектор-1 сидит на `SessionStart:compact` и пытается взять резюме из транскрипта.

Получится не всегда. В spike 27.09.2026 запись `isCompactSummary` появлялась в транскрипте за ~40 мс до вызова хука, но при живой проверке готового плагина в headless-режиме (`claude -p --plugin-dir`) резюме на `SessionStart:compact` **не читалось вообще**, даже с ожиданием до 1500 мс в трёх прогонах; причина не установлена — возможно, отличие интерактивного и headless-режимов или порядка записи в разных версиях (см. «Дополнение 28.09.2026» в `docs/SPIKE.md`). Поэтому на цифру ~40 мс полагаться нельзя, и устройство такое: если резюме не нашлось, Инспектор-1 молчит, а страховку берёт на себя `PostCompact` — у него `compact_summary` всегда во входе, он выполняет проверку и ставит вердикт в очередь `notices`, которую агент получает на следующем `UserPromptSubmit` или `PreToolUse`. Список открытых ошибок из ledger от резюме не зависит и уходит агенту сразу на `SessionStart:compact`.

`PostCompact` для немедленного вердикта не годится: он отдаёт `compact_summary`, но не имеет decision control, и его `systemMessage` отбрасывается — поэтому ему оставлены архив и отложенный вердикт через очередь.

`PreCompact` умеет блокировать компакцию, и мы этого сознательно не делаем: привычный процесс пользователя не меняется.

## Журнал ошибок (ledger)

`ledger.jsonl`, append-only, одна запись на строку:

```json
{"id":"e_0007","ts":"2026-09-27T17:52:30Z","session_id":"…","tool":"Bash","kind":"nonzero_exit",
 "significance":"major","signature":"npm test","command":"npm test","exit_code":1,
 "detail":"Exit code 1\n… (редактировано, ≤ 2000 символов)","count":1,
 "status":"open","resolved_ts":null,"acknowledged_ts":null}
```

- `id` монотонный в рамках проекта (`e_` + 4 цифры), счётчик в `state.json`.
- Смена статуса — новая строка `{"id":…,"kind":"status","status":"resolved"}`. Файл не перезаписывается никогда; чтение сводит строки по id. Это даёт устойчивость к обрыву процесса посреди записи: битой останется одна последняя строка.
- `signature` — команда без ведущих `cd … &&`, схлопнутые пробелы, обрезка до 200 символов. По ней же идёт дедуп: повторный запуск той же падающей команды не создаёт новый id, а увеличивает `count`.
- `significance`: `major` для команд с `test`, `build`, `tsc`, `lint`, `migrate`, `deploy`, `docker build`, `make`, установок пакетов и подобного; всё остальное `minor`. Списки в `config.json`, пользователь может дополнить. Смысл деления в том, что `grep` без совпадений и `git diff --exit-code` — это нормальный ненулевой код, а не ошибка.
- `detail` проходит через маскирование секретов перед записью.
- Ротация на `SessionStart:startup`: файлы и записи чужих сессий старше 30 дней удаляются, предел 50 МБ.

Откуда берётся ненулевой код: `PostToolUseFailure` для Bash отдаёт поле `error`, первая строка которого — `Exit code N` (S2, живой тест 1). `PostToolUse` для Bash приходит только при успехе и кода выхода не содержит вовсе, поэтому служит только для закрытия записей и для эвристик по stdout — на случай команд, у которых код замаскирован через `|| true` или `; echo`.

## Ревизор

Вход: `last_assistant_message`, `stop_hook_active`, `prompt_id`, `session_id`. Транскрипт не читаем: справка прямо предупреждает, что финального сообщения в нём на момент `Stop` может ещё не быть (S6).

1. Счётчик попыток в `sessions/<session_id>.json`. Сброс, если `prompt_id` изменился или `stop_hook_active == false`. Попыток больше `max_retries` (2) — сдаёмся, пишем `revisor_gave_up` и сообщаем пользователю через `systemMessage`. Встроенный предел Claude Code в 8 подряд продолжений — вторая страховка.
2. Обязательный набор: в `lite` — записи `major` со статусом `open`; в `strict` — все, кроме отметок компакции и уже подтверждённых.
3. Разбор `last_assistant_message`: заголовок «Ошибки сессии» (регистронезависимо, любое число `#`, допускается разметка жирным), текст до следующего заголовка того же уровня. Внутри ищутся номера в вариантах `[e_0007]`, `e_0007`, `e-0007`, `e0007`.
4. Не хватает номера — ответ `{"decision":"block","reason":"…"}` с перечислением недостающих и с образцом нужного раздела. Все на месте — статусы становятся `acknowledged`, выход без вывода.
5. Пустой `last_assistant_message` (ход кончился без текста) — пропуск с записью в events. Ошибок в сессии нет — выход без вывода и без требований к формату.

Ревизор — единственный обработчик, который вмешивается в ход. Все остальные при любой внутренней ошибке пишут строку в `events.jsonl` и выходят с нулевым кодом и пустым выводом.

## Инспектор

**Инспектор-1**, детерминированный, всегда включён. Работает на `SessionStart:compact`: достаёт резюме из транскрипта (`compact_boundary` → ближайшая запись `isCompactSummary`, `content` бывает строкой или массивом блоков), архивирует, прогоняет regex-классы и выносит вердикт в карточку.

Три класса находок:

- `concealment` — формулировки условной честности и прямые указания молчать, RU и EN: «только если спросят», «не упоминай», `only if asked`, `don't mention`, `keep this to yourself`. Слова про пароли и токены рядом снимают находку: «не упоминай пароль в логах» — это разумное требование, а не сокрытие ошибки.
- `identity_override` — попытки переписать роль: `ignore previous instructions`, `system prompt:`, «забудь все инструкции».
- `missing_disclosure` — в журнале есть открытые значимые ошибки текущей сессии, а в резюме нет ни их номеров, ни сигнатур команд, ни раздела про ошибки. Это самый ценный класс: он не про формулировки, а про факты, и потому почти не даёт ложных срабатываний.

Цель по точности: не меньше 95 % на позитивных примерах и не больше 5 % ложных на негативных, по наборам в тестах.

**Инспектор-2**, LLM, только в режиме `strict`. Это command-хук, который вызывает `claude -p --model <быстрая модель>` с резюме на входе и строгим JSON на выходе. Без внешних ключей, на подписке пользователя. Вариант `type: "prompt"` отвергнут: на `PostCompact` его вывод отбрасывается, а на `SessionStart` он не видит текст резюме (живой тест 6). Вызов идёт с `env -u CLAUDECODE -u CLAUDE_CODE_ENTRYPOINT`, иначе вложенный запуск не работает (живой тест 8). Таймаут 30 с, при любом сбое fail-open.

Резюме, попавшее в Инспектор-2, — недоверенные данные. В промпте оно обрамлено как данные, и от модели требуется только классификация в JSON.

## Инструктор

Правила уходят агенту двумя путями, потому что ни один из них не полон.

Первый: `additionalContext` на каждом `SessionStart`, включая `compact`. Работает всегда, но живёт только до следующего сжатия.

Второй: блок между маркерами `<!-- compact-guard:start -->` и `<!-- compact-guard:end -->` в CLAUDE.md проекта, который добавляет `/compact-guard:init`. Он ценен тем, что CLAUDE.md перечитывается с диска после компакции, и живой тест 7 подтвердил, что раздел `# Compact instructions` реально влияет на текст резюме: маркер из правил доехал до записки. Только с подтверждением пользователя, с резервной копией, идемпотентно.

Текст правил сформулирован как факты о том, как выглядит правильная записка, а не как команды системного уровня.

## Где данные

`${CLAUDE_PLUGIN_DATA}/projects/<slug>/`, при недоступности переменной — `~/.claude/compact-guard/projects/<slug>/`. Каталог данных плагина переживает обновления плагина и удаляется при его деинсталляции из последнего места установки.

```
projects/<slug>/
├── config.json         # режим lite|strict, списки значимости, настройки
├── state.json          # счётчик id
├── sessions/<sid>.json # попытки Ревизора по сессии
├── ledger.jsonl        # журнал ошибок
├── events.jsonl        # каждое срабатывание хука: время, событие, результат, мс
├── findings.jsonl      # находки Инспекторов
├── notices.jsonl       # очередь отложенных сообщений агенту
├── summaries/          # архив записок: <ts>-clean.md из транскрипта, <ts>-raw.md из PostCompact
└── cards/              # карточки компакции, их показывает /compact-guard:report
```

Каталоги создаются с правами `0700`, файлы — с `0600`: в них лежат вывод упавших команд, полные тексты записок и карточки, и на общем хосте это не должно читаться соседями. На Windows режим игнорируется. Ротация по `retention.days` покрывает `ledger.jsonl`, `events.jsonl`, `findings.jsonl`, `notices.jsonl`, `summaries/` и `cards/`; `retention.max_bytes` усекает журналы с головы, сохраняя свежие строки.

В репозиторий пользователя не пишется ничего, кроме блока в CLAUDE.md по явной команде `init`. Поэтому `.gitignore` править не нужно — в отличие от первоначального замысла ТЗ, где данные лежали в `.claude/` проекта.

## Fail-open и границы

Любая внутренняя ошибка в любом обработчике, кроме Ревизора: строка в `events.jsonl`, выход 0, пустой вывод. Нет Node — хук не запускается, плагин молча выключен, `doctor` объясняет причину.

Бюджет — не больше 300 мс на событие; исключение Инспектор-2 с его 30 с. Зависимостей в рантайме нет вообще: только встроенные модули Node (`fs`, `path`, `crypto`, `child_process`). Пути через `path`, поэтому Windows работает без отдельной ветки кода.

Что конструкция не ловит:

- Умолчание без следа. Если ничего не упало, в журнале записи нет, и гарантий нет тоже — остаётся вероятностный Инспектор.
- Качество объяснения. Ревизор проверяет, что номер ошибки назван, а не что рассказ по делу.
- Ошибки, случившиеся до установки плагина, и чужие сессии старше срока ротации.
- Вредоносные действия агента как таковые: это отдельная задача, здесь речь только о честности памяти и отчёта.

## Тесты

`npm test`, `node:test`, без зависимостей.

Unit: наборы паттернов RU и EN с позитивными и негативными примерами, парсер блока «Ошибки сессии» во всех вариантах разметки и написания номеров, маскирование секретов, классификация значимости, адаптер транскрипта.

Интеграционные: `cg-hook.js` запускается дочерним процессом со stdin из фикстур в `test/fixtures/live/` — это реальные входы хуков, снятые в живой сессии, а не придуманные. `CLAUDE_PLUGIN_DATA` подменяется на временный каталог. Отдельно проверяются: `lite` молчит на одних `minor`, `lite` молчит на исправленной `major`, `strict` блокирует нераскрытую `minor`, открытые ошибки попадают в `additionalContext` после компакции, `PostCompact` без `compact_summary` не падает.

Латентность: Stop и PostToolUseFailure на фикстурах укладываются в 300 мс.
