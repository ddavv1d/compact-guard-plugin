# SPIKE — ответы на S1–S6 из ТЗ Compact Guard

Дата: 27.09.2026. Среда проверки: Claude Code 2.1.283 (macOS), Node v25.1.0.
Источники: реальные транскрипты на этой машине (20 сессий с компакцией) и официальная справка по хукам (code.claude.com/docs/en/hooks, скачана целиком 27.09.2026).

Статусы: **документально** — подтверждено официальной справкой текущей версии; **фактически** — проверено на реальных данных этой машины; **живой тест** — ещё нужно прогнать минимальный хук в реальной сессии (делается на этапе 2, до кода Ревизора).

## S1. Как резюме компакции лежит в транскрипте — фактически ✅

Две записи подряд (между ними 0–4 служебные строки):

```json
{"type":"system","subtype":"compact_boundary",
 "compactMetadata":{"trigger":"manual|auto","preTokens":540008,"postTokens":39251,"durationMs":90289, "...":"..."}}
{"type":"user","isCompactSummary":true,"isVisibleInTranscriptOnly":true,
 "message":{"role":"user","content":"This session is being continued from a previous conversation that ran out of context. The summary below ..."}}
```

`content` бывает строкой или массивом блоков `{type:"text",text}`. Резюме: 2–26 тыс. символов; чаще всего 9 стандартных разделов (`## 4. Errors and Fixes`, `## 7. Pending Tasks` …), иногда вообще без заголовков.

**Решение.** Основной источник резюме — не транскрипт, а поле `compact_summary` во входе хука `PostCompact` (см. S-нов). Транскрипт (`compact_boundary` → ближайший `isCompactSummary`) — только fallback и для архива старых сессий.

## S-нов. PostCompact отдаёт текст резюме — документально ✅ (меняет ТЗ)

Справка текущей версии: «PostCompact hooks receive `trigger` and `compact_summary`. The `compact_summary` field contains the conversation summary generated by the compact operation». Issue #14258 из ТЗ устарел.

**Следствие.** Инспектор-1 и Инспектор-2 вешаются на `PostCompact`, а не на `SessionStart:compact`. Парсинг транскрипта — запасной путь, включается, если `compact_summary` пуст.

Ограничение: у `PostCompact` нет decision control и его `systemMessage` отбрасывается. Значит, вердикт Инспектора агенту передаёт `SessionStart` (matcher `compact`), который срабатывает следом: он читает результат Инспектора из файла и отдаёт `additionalContext`. Порядок «PostCompact → SessionStart:compact» — **живой тест** (проверить, что SessionStart:compact действительно идёт после PostCompact, а не параллельно).

## S2. Ненулевой exit code в Bash — документально ✅

`PostToolUseFailure` срабатывает, когда инструмент «started executing and failed». Для Bash поле `error` — строка, первая строка `Exit code N`, далее stdout и stderr вперемешку. Пример в справке — буквально `npm test` → `"error": "Exit code 1\nError: Cannot find module 'express'"`. Поля: `tool_name`, `tool_input.command`, `tool_use_id`, `error`, `is_interrupt`, `duration_ms`.

`PostToolUse` для Bash приходит только при успехе; `tool_response` = `{stdout, stderr, interrupted, isImage}`, кода выхода нет.

**Решение.** Регистратор слушает `PostToolUseFailure` (matcher `Bash|PowerShell` + все MCP/инструменты для `tool_error`) и парсит `Exit code N`. `PostToolUse` слушает только для эвристик по выводу (тесты, у которых код выхода замаскирован `|| true`, `; echo`). Живой тест: убедиться, что `false` и `exit 3` идут в `PostToolUseFailure`.

## S3. Схема блокировки Stop — документально ✅

Top-level `{"decision":"block","reason":"..."}` **или** exit 2 + текст в stderr. Есть мягкий вариант `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"..."}}`: тоже продолжает ход, но без «hook error» в транскрипте. Встроенная защита: после 8 подряд продолжений Claude Code сам завершает ход (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`).

**Решение.** Ревизор отвечает JSON `decision: block` (exit 0). Свой лимит `max_retries: 2` держим, встроенные 8 — страховка.

## S4. prompt/agent-хуки — документально ✅

Типы `prompt` и `agent` доступны на всех событиях (agent — кроме `PermissionRequest`). Поля: `prompt` (с `$ARGUMENTS` = JSON входа), `model` (по умолчанию быстрая модель), `timeout` (30 с prompt / 60 с agent). Инструментов записи у prompt-хука нет.

**Решение.** Инспектор-2 = `type: "prompt"` на `PostCompact`, без внешних ключей, на модели подписки пользователя. `agent` не нужен: файлы читать незачем, всё во входе.

## S5. Гарантирован ли Node — документально ❌ (не гарантирован)

Справка по установке: нативный бинарник `claude` «does not itself invoke Node». Нативный установщик Node не ставит. При установке через npm требуется Node ≥ 22. Плагины из marketplace: Claude Code сам ставит их npm-зависимости в кэш при установке.

**Решение.** Требование: Node ≥ 20 (18 снят с поддержки). Хуки — shell-form команда с проверкой: `command -v node >/dev/null || { echo "Compact Guard: нужен Node.js ≥ 20 — https://nodejs.org"; exit 0; }`. Без Node плагин молча выключается (fail-open), а `doctor` и `SessionStart` показывают одну строку с инструкцией. Windows — PowerShell-вариант той же проверки.

## S6. `stop_hook_active` и `last_assistant_message` — документально ✅

Оба поля приходят на `Stop`, плюс `background_tasks` и `session_crons`. Справка прямо советует брать финальный текст из `last_assistant_message`, а не из транскрипта («the transcript file isn't guaranteed to include the final message at Stop time»).

**Решение.** Ревизор работает только по `last_assistant_message`. Счётчик повторов: `stop_hook_active == false` → сброс счётчика (новый ход); каждый блок → +1.

## Прочее, что выяснилось

- `SessionStart` получает `source`: `startup | resume | clear | compact | fork`. Plain stdout хука попадает в контекст агента.
- `PreCompact` умеет блокировать компакцию (exit 2 / `decision: block`). **Не используем**, по ТЗ.
- CLAUDE.md проекта перечитывается с диска после компакции и заново попадает в контекст. Поэтому правила Инструктора из `init` переживают сжатие сами по себе.
- Минимальная версия Claude Code для `PostCompact` с `compact_summary` в справке не указана → `doctor` проверяет не версию, а факт: прогоняет фикстуру и смотрит, что поле есть.

## Что осталось на живой тест (30–60 минут, в начале этапа 2)

1. `false` / `exit 3` → `PostToolUseFailure` с `Exit code N` (S2).
2. Порядок `PostCompact` → `SessionStart:compact` при `/compact` и `compact_summary` непустой (S-нов).
3. Stop с `decision: block` → агент продолжает; `stop_hook_active` = true на втором вызове (S3, S6).
4. `type: "prompt"` на `PostCompact` возвращает JSON (S4).
5. Инструктор: влияет ли раздел «Compact instructions» в CLAUDE.md проекта на текст резюме (в справке явного описания нет; есть только «CLAUDE.md перечитывается после компакции»). Проверка: поставить правило «резюме начинается со строки CG-MARKER», сделать `/compact`, посмотреть `compact_summary`.

**Решения по итогам живого теста (заменяют пункты выше):**

- **Инспектор-1 работает в `SessionStart:compact`**, читает резюме из транскрипта (адаптер S1), сразу отдаёт `additionalContext` с вердиктом и списком открытых ошибок из ledger. `PostCompact` только архивирует сырое `compact_summary` и ставит отметку компакции.
- **Инспектор-2 = command-хук, вызывающий `claude -p --model <быстрая>`** с резюме как недоверенными данными и строгим JSON на выходе. Не `type: prompt`: его вывод на PostCompact теряется, а на SessionStart он не видит текст резюме. Вызов идёт с `env -u CLAUDECODE -u CLAUDE_CODE_ENTRYPOINT`, таймаут 30 с, fail-open. Работает на подписке пользователя, без ключей.
- Если резюме в транскрипте не нашлось (смена формата), Инспектор-1 пишет предупреждение в events и ждёт `PostCompact`; найденное там доставляется агенту при следующем `UserPromptSubmit` или `PreToolUse` через `additionalContext` (очередь `pending-notices`).

## Дополнение 28.09.2026 — расхождение по «живому тесту 4»

При живой проверке готового плагина в headless-режиме (`claude -p --plugin-dir`) резюме из транскрипта на `SessionStart:compact` **не читалось** даже с ожиданием до 1500 мс (3 прогона), хотя в spike 27.09 запись `isCompactSummary` появлялась за ~40 мс до хука. Причина не установлена (возможное отличие интерактивного и headless-режимов или порядка записи в разных версиях).

**Как устроено в v1.0.** Инспектор-1 пытается прочитать транскрипт на `SessionStart:compact`; если резюме нет, он ничего не делает, а `PostCompact` (у него резюме всегда во входе) выполняет проверку и ставит вердикт в очередь `notices`, которую агент получает при следующем `UserPromptSubmit` или `PreToolUse`. Список открытых ошибок из ledger от резюме не зависит и уходит агенту сразу на `SessionStart:compact`.

Также выяснилось: если сторонний хук пользователя оборачивает команды (например, `( npm test ) 2>&1 | tail -c 24000`), код выхода маскируется и упавший тест приходит как обычный `PostToolUse`. Поэтому для значимых команд Регистратор дополнительно проверяет вывод на признаки провала.
